# PDF 审核结果单设计

## 目标

审核完成后，用户既可下载现有 Word 详细报告，也可下载一份适合教师快速查看和纸质提交的单页 PDF 摘要。PDF 是新增产物，不替换 Word 报告，也不把长篇 Word 报告转换为 PDF。

## 架构与数据来源

审核引擎仍负责 DOCX 批注、完整 Word 报告和 JSON 审核结果。平台 worker 在同一次审核完成时读取同一份 JSON，结合平台数据库的学生档案生成 PDF，并将 PDF 与 Word 报告存入同一个 attempt 目录。审核事实来自 JSON；身份信息来自平台档案；提交及完成时间来自提交记录。PDF 不推断学院等平台未保存的数据。

PDFBox 负责固定版式，中文字体在生成时嵌入。生成器必须明确处理长字段并校验最终页数严格等于一页。若 JSON 无法解析、字体无法加载或输出版面超出一页，审核不能把 PDF 标为可用。

## 报告内容和统计

PDF 显示论文文件名、学生姓名、学号、专业、指导教师、提交编号、完成时间、规则版本、明确问题数、待确认数、批注写入概况和源文件短指纹。报告明确说明：问题数来自 `results` 中 `FAIL` 项；待确认数来自 `REVIEW` 项，未计入问题数；没有执行证据的检查不能算作通过。批注状态来自同一次审核的 annotation 结果。

PDF 不列出逐条问题、全部规则编号、XML 路径或未执行规则全集；这些仍由 Word 详细报告承载。没有学院字段时不显示学院。

## 数据流和接口

`AuditEngine.Result.reportJson` → `PdfSummaryReportWriter` + 提交/学生/指导教师档案 → `attempt-N/report.pdf` 与现有 `report.docx`、`report.json` 一并持久化 → 在 PDF 上传成功后发布审核 SUCCESS → 通过现有提交详情接口暴露独立 PDF 可用状态 → 详情页提供独立 PDF 下载。

下载类型为 `report-pdf`，对象键和文件名均由服务端生成；二进制下载与 COS 预签名下载沿用学生本人/指导教师权限和当前成功 attempt 检查。直接流式响应使用 `application/pdf`。原有 `report` 始终指向 Word DOCX。

Flyway 新增独立 PDF 可用列，默认 `false`；旧成功记录继续下载原 Word 报告，但不展示不存在的 PDF。新审核仅在 DOCX、JSON、批注稿及 PDF 的持久化全部完成后才发布 SUCCESS。

## 失败与安全

PDF 生成或上传失败时，不得发布部分成功的报告状态；使用既有 attempt 失败与清理机制。权限在生成下载计划和实际开始流式读取时复核，不接受客户端任意对象键。报告不包含登录凭证、COS 签名或未授权的其他学生数据。

## 验收

生成器验证严格一页、中文字体嵌入、中文文本可提取、统计口径、长字段和字体缺失错误。平台验证旧记录迁移、PDF 持久化失败、attempt 隔离、内容类型、文件名、授权、预签名和 Word 报告兼容。前端验证成功记录显示两个报告入口，缺少 PDF、处理中及失败记录不显示 PDF 入口，并覆盖代理和预签名下载路径。

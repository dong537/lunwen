# DOCX 论文格式规则完善设计

## 目标

在现有毕业论文格式检测系统上，完善能够由 DOCX/OOXML 直接证明的格式规则。系统对确定的错误直接输出“格式错误”，并在对应段落或对象上写入一条具体修改建议；不输出“人工复核”状态。

## 范围

本阶段只处理 DOCX/XML 可稳定读取的内容：

- 参考文献编号、类别、字段、字体、字号、行距和正文引用；
- 表题、表号、三线表、单元格边框、合并、尺寸、表头单位、表注和重复占位文字；
- 图片尺寸、变形、题注格式、题注位置和正文引用；
- OMML 公式的字体、斜体、上下标、分式、矩阵、编号和正文引用；
- 参考文献和致谢标题的空行、空格和标题格式。

本阶段不把 Word/LibreOffice 最终分页结果伪装成 XML 结论。表格跨页、图题同页、题注与对象的实际视觉距离属于后续 PDF 版面分析阶段。

## 设计

`RuleEngine` 保留为总编排入口，新增规则逻辑按领域放入独立检查器，避免继续扩大单个方法的复杂度：

- `ReferenceRuleChecker`：接收 `ParsedDocument` 和参考文献模型，返回 `CheckResult`；负责编号顺序、类型、字段完整性、引用关系和引用格式。
- `TableRuleChecker`：接收扩展后的 `TableModel` 和段落索引，负责题注、边框、单元格结构、单位、表注和正文引用。
- `ImageRuleChecker`：接收扩展后的 `ImageModel`，负责尺寸、变形、题注和正文引用。
- `EquationRuleChecker`：接收扩展后的 OMML 模型，负责内部格式、编号连续性和引用。

检查器只返回领域结果，不负责批注写入。`CommentWriter` 根据 `ruleId` 和 `reasonCode` 生成自然、具体的修改建议；同一段落同一规则只保留一条批注。

## 数据模型和证据

解析器必须保留每个错误的 `SourceAddress`，使结果和批注能定位到原始 XML 节点。新增字段只保存规则确实需要的证据：

- 表格：单元格边框、合并信息、列宽、行高、表注候选和表头文本；
- 图片：原始 EMU 尺寸、显示尺寸、变形比例和锚点信息；
- 公式：OMML 节点类型、字体、字号、斜体、上下标和结构节点；
- 参考文献：编号、类别、正文结构字段和首次引用地址。

无法读取或无法证明的字段按项目既有契约转换为直接错误，批注说明缺失的格式证据或具体修改动作；不得静默当作通过。

## 判定契约

- `PASS`：XML 中明确满足规则。
- `FAIL`：XML 中明确不满足规则，或文档明确缺少必需结构。
- 对外 API 将内部非确定状态统一转换为 `FAIL`，前端只显示“通过/格式错误”。
- 只有失败结果写入批注；同一个段落大量重复错误按规则合并。
- 原始 DOCX 永远不原地修改，只生成带批注副本。

## 实现顺序

1. 扩展解析模型和解析器，补齐 SourceAddress 与 XML 证据。
2. 为每个新增规则编写失败测试和通过测试。
3. 接入领域检查器和统一结果映射。
4. 增加批注文案和颜色映射。
5. 运行后端完整测试、前端构建、DOCX 解包完整性检查。
6. 用真实论文验证错误数量、批注数量、无 `REVIEW` 输出和原文不变。

## 验证标准

- `mvn verify` 通过。
- `npm run build` 通过。
- `git diff --check` 通过。
- 合成 DOCX 覆盖每个新增规则的通过、失败、缺失和边界样本。
- 真实论文接口结果中不存在对外 `REVIEW`。
- 带批注 DOCX 可被 docx4j 重新打开，且包含预期 `comments.xml` 和关系声明。

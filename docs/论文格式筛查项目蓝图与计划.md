# 论文格式筛查项目蓝图与计划

日期：2026-10-03。状态：早期草案，未开始实现。2026-10-04 用户明确要求先完成开源、XML 准确性与效率研究，再设计；本文件的技术栈、架构和页面设想均未冻结，以研究结论和后续设计确认为准。

## 1. 目标与范围

任务模式：规划模式；本次仅产出文档，不创建业务代码、页面或部署资源。

面向学校论文提交者及检查人员，提供统一入口：上传 DOCX，选择适用规则，查看检测进度，阅读带原文定位和判定依据的报告，下载报告。不区分教师端、学生端。按用户最新要求，首版不实现登录注册、账户管理和用户隔离，采用本机或受控内网的共享工作区。

成功标准：明确规则能够被重复、可解释地检测；解析失败、未知属性和不支持对象不会被判为合格；报告能说明位置、学校要求、实际值与依据。所有适用规则均产生通过、不通过或需复核结果，未运行项有原因，覆盖率不能用问题数量代替。

第一版不做：论文查重、AI 写作检测、内容评分、自动修改论文、审批流程、多学校管理、在线规则编辑器、旧 DOC/PDF 输入。PDF 报告导出不等于支持 PDF 论文检测。

## 2. 权威来源与规则确认

来源为用户提供的《论文规范.docx》。实施时计算文件 SHA-256 并保留只读来源副本；该微信目录不进入生产配置。

优先级：学校确认的规则版本 > 规范明确文字 > 模板示例推断。每条规则保存来源说明、适用区域、专业、期望值、单位、严重程度和确认状态。模板实际格式不能自动成为标准。

已发现：模板某节右边距约 2.5 cm，与四边 2.6 的说明不符；存在 Equation.3 对象；公式居中与编号居右的措辞有歧义；部分专业允许另定要求。

编码前需要确认的决策：

- 推荐首版采用通用专业规则，专业例外没有确认前不参与自动判定。
- 用户已确认：所有节上、下、左、右页边距严格按 2.6 cm 执行。常用整数 twips 表示量化为 1474；模板中的 1418 不合格，不用模板错误覆盖规则。
- 正文行距适用范围、空一行的判定方式、全角/半角空格是否等价需确认。
- 公式主体居中、编号居右仅为候选解释，尚未确认，不作为已确认硬规则；原文另明确编号五号 Times New Roman、按章编序及附录特例，见第八轮研究。公式主体字号未明确，不自行规定。
- 英文关键词加粗范围、英文摘要“实词”和正文字符计数口径需确认。
- 页眉适用范围、目录条目格式等仅有模板证据的项目先标为待确认。
- “一般”“最好”“必要时”等要求按建议或人工复核处理，不升级为硬性错误。

## 3. 技术路线

推荐暂定 Java + Spring Boot，前端 React + TypeScript + Tailwind CSS。Java 是规划假设，并非用户已确认的强制要求。

| 路线 | 收益 | 成本与限制 |
| --- | --- | --- |
| Java + docx4j，按需读取底层 OOXML | 便于学校业务系统维护，直接分析 DOCX | 有效格式、旧公式和实际分页需验证；解析不等于渲染 |
| Java + 商业文档组件 | 可能同时满足解析、渲染、页码定位 | 授权费用与部署条件；必须实测，不能假设与 Word 完全一致 |
| C#/.NET + Open XML SDK | 适合精细 OOXML 处理 | 不自带 Word 排版能力，仍有相同渲染与旧公式问题 |

先验证 Java 开源路线，商业组件仅在试验中比较。若关键能力不满足，记录证据后调整组件或技术路线，不同时建设两套后端。

数据库 PostgreSQL；使用 JPA/Hibernate 与 Flyway 管理业务数据和显式迁移。持久化后台任务优先评估 db-scheduler，复用 PostgreSQL；调度库拥有自己的表与访问实现，业务层不绕开 ORM。采用模块化单体代码库、API/worker 分进程部署、渲染隔离进程的架构，先不引入 Redis、Kafka 或微服务。

2026-10-03 的早期开源调研见 [技术研究与架构决策](research/开源选型与Word准确解析架构.md)。截至 2026-10-04，Java/docx4j 已有 33 项研究测试通过，独立 MTEF 精度探针仍失败；完整产品尚未验收。当前规则与能力边界以 [学校规则矩阵与核心验收清单](research/学校规则矩阵与核心验收清单.md) 及各轮实测报告为准。

单校部署优先持久化文件卷，文件服务封装存取与删除状态校验；只有需要多实例或已有对象存储时才选择 S3 兼容存储。配置来自环境变量和 Secret，不内联密钥或生产地址兜底。

## 4. 核心模型与模块边界

| 模型 | 数据及责任 |
| --- | --- |
| Document | 原文件、哈希、存储位置、有效期；原件不可变，不关联账户 |
| RuleSet / Rule | 经确认的规则及版本；已发布版本不可变 |
| InspectionJob | 文档、规则版本、解析器版本、状态、重试次数和错误 |
| ParsedDocument | 章节、段落、文字片段、有效样式、表格、图片、公式及来源定位；派生数据 |
| Finding / Report | 规则结果、期望值、实际值、证据、定位、复核原因和覆盖统计 |

模块：

- ingestion：文件校验、安全解包和入库；限制压缩包展开体积、条目数与执行时间，不执行 OLE，不抓取外部关系资源。
- document：DOCX adapter、样式继承计算、内容区域识别和稳定定位；保留属性来源，未知值不默认化。
- rules：规则匹配、单位换算、编号与引用校验；不依赖 Web 或 UI。
- inspection：任务编排、状态转换、失败处理、幂等与结果持久化。
- reporting：组织结果、覆盖说明、原文片段、报告导出；可选渲染 adapter 提供页码证据。
- 文件保留、删除和操作记录归 ingestion/inspection，不建立账户或认证模块。
- 前端 features：上传、任务列表、报告；页面只组合，不内嵌检测规则。

不要为了未来扩展创建通用插件框架。只有真实替换需要的文档组件、存储等外部依赖建立适度 adapter。

## 5. 数据流与接口契约

上传 DOCX → 校验并保存原件 → 创建固定规则版本的任务 → 后台解析 → 计算有效格式并识别区域 → 运行检测 → 持久化报告 → 前端查询和导出。

学校规则集通过版本化发布进入后端；前端只显示后端结果，不复制判定逻辑。重新检测创建新任务，保留旧报告对应的规则版本。

建议 API：创建检测任务、分页查询共享任务列表、查询任务状态、查询/筛选报告、下载报告、删除终态任务及关联文档结果。上传上限与保留期限在部署前配置并显示给用户。

统一成功响应包含 data、requestId；错误包含 code、message、details、requestId，并使用正确 HTTP 状态。错误类别至少区分非法文件、文件过大、文档受保护、解析失败、资源超限、无权访问、任务失败和报告生成失败。

分页使用 page/pageSize/total；排序字段白名单，默认创建时间降序；报告可按章节、对象类型、规则和判定筛选。ID 使用不透明字符串；服务端保存 UTC 时间，界面按 Asia/Shanghai 展示；字号统一 pt，边距统一 mm，字符缩进与物理长度保留不同类型。

任务生命周期：queued → parsing → checking → completed / failed。completed 表示任务完成，不表示论文合格。结果未覆盖全部适用项时必须显示需复核/未检测原因。队列异常重启、超时与重试需有明确状态及审计；失败不返回空报告。

## 6. 检测范围

第一组：章节与区域识别、字体/字号/粗体、中西文字体、段落缩进/行距、标题层级、分节页边距、封面和摘要、关键词与参考文献。

第二组：图表题注、位置关系、按章编号、正文引用、表格边框与续表；正文与附录使用不同编号规则。

第三组：原生 OMML、Equation.3、其他 OLE 及图片公式分类，公式编号与引用、编号样式、变量说明复核。旧公式内部不能可靠读取时明确说明，不能漏检或按普通图片判为合格。

渲染相关：页码与目录页码一致性、图题同页、跨页表格、公式位置。必须在选定渲染环境下验收；缺少渲染能力时这些项目明确不支持自动判定。

不从规范中虚构图片宽高/DPI、公式主体字号或表格文字字号要求。截图来源、变量解释充分性等只做复核提示。

## 7. 页面与最小设计约定

统一入口包含上传页、任务列表、报告详情；无师生分端。

主流程：上传页明确 DOCX 限制和适用规范 → 列表显示可解释进度与失败原因 → 报告首屏显示检测是否完整、问题数量和复核项 → 按章节查看证据 → 下载报告。

报告同时展示期望值、实际值、规则来源和原文片段。默认定位到章节/段落/对象；未经渲染验证的页码不展示为精确位置。图片位置不能仅按 XML 顺序推断视觉上下关系。

server state 使用 TanStack Query，表单使用 React Hook Form + Zod，筛选保存在 URL，临时展开状态留在组件。中文为首版语言，文案集中管理以支持后续 i18n，不加入语言切换器。

目标视口：320、375、768、1024、1440 px 与 200% 缩放。覆盖 initial、loading、empty、error、permission、pending、success、retry、部分项目需复核状态。报告不能只靠颜色表达结果；键盘可完成上传、筛选、查看与下载。

## 9. 分阶段执行与验收

### 阶段 1：规则冻结与样本准备

- [ ] 将规范拆为带来源、单位、区域和确认状态的规则清单。
- [ ] 解决本文件第 2 节的歧义；未解决项不能启用为硬性规则。
- [ ] 收集经授权的真实论文并脱敏，准备人工标注；模板不能充当唯一合格样本。
- [ ] 为每类明确规则准备合格、违规和不适用样本。

交付：规则版本 1、标注样本和争议决策记录。验收：每条硬性规则都有明确来源、边界与预期结果。

### 阶段 2：解析与渲染能力试验

- [ ] 验证直接格式、继承样式、中西文混排、字符缩进与厘米缩进、分节和页码。
- [ ] 验证浮动图片、三线表、跨页表格、OMML 与模板实际使用的 Equation.3。
- [ ] 比较所选组件与学校指定 Word/WPS 环境的关键排版差异。
- [ ] 记录旧公式能力、定位精度、耗时/内存、授权及部署字体要求。

交付：选型报告及能力矩阵。验收：明确哪些检查可确定性执行，哪些需渲染，哪些必须人工复核；据此锁定技术栈与承诺范围。

### 阶段 3：检测内核

- [ ] 先为已确认规则编写会失败的行为测试，再实现有效格式解析和区域识别。
- [ ] 实现正文、标题、摘要、封面、关键词、页边距和参考文献规则。
- [ ] 实现图表与公式编号、题注和引用；附录单独匹配。
- [ ] 输出稳定定位、实际值与来源证据，验证未知/不支持/失败状态。

交付：通过公共接口运行的真实 DOCX 检测内核。验收：冻结样本预期结果全部通过；另用独立人工标注样本逐规则报告误报、漏报与覆盖，不能用单一总准确率掩盖漏检。

### 阶段 4：上传、任务与报告闭环

- [ ] 建立数据库迁移、持久化文件存储和可靠任务执行。
- [ ] 实现上传、状态查询、报告筛选和导出。
- [ ] 实现文件保留/删除与操作记录；不实现登录注册或账户功能。
- [ ] 验证重复提交、服务重启、解析超时、损坏文件和导出失败。

交付：可通过 API 跑通的完整闭环。验收：真实 PostgreSQL、真实文件与真实检测器集成测试通过；他人不能获取文件/报告；失败可追踪，任务不会在重启后悄悄消失。

### 阶段 5：统一前端

- [ ] 冻结上传、列表和报告页面 manifest，再实现 React 页面。
- [ ] 显示明确错误、处理进度、未覆盖规则及需复核项。
- [ ] 通过浏览器验证完整上传→检测→定位→导出流程。
- [ ] 验证键盘、焦点、窄屏、200% 缩放、长文件名/长章节名、无问题和大量问题报告。

交付：统一用户界面与浏览器验证证据。验收：核心流程有真实可见结果，无运行时错误、意外横向溢出和不可达操作；功能硬门通过后再做视觉复核。

### 阶段 6：部署与学校试用

- [ ] Docker 多阶段构建、非 root 运行、健康检查、持久化卷和优雅退出。
- [ ] CI 执行后端测试/构建、前端 typecheck/lint/test/build；实际命令以工程脚本为准。
- [ ] 记录 requestId/jobId/ruleVersion，监测任务耗时、失败率和队列积压；日志不包含论文全文。
- [ ] 执行镜像构建、启动、健康检查和真实论文 smoke check；验证备份恢复与显式迁移步骤。
- [ ] 由学校人员复核试用报告，修正规则版本；旧报告保留历史规则与解析器版本。

交付：可部署版本、运维说明、试用问题清单和发布记录。验收：业务 smoke check 与数据持久化验证通过；未通过的规则不得宣传为已支持。

## 10. 发布与回滚

应用镜像与规则版本分别固定。发布前备份数据库和文件元数据；数据库迁移显式执行，不在业务请求中自动修复 schema。回滚需同时核对数据库兼容性，必要时从验证过的备份恢复，不只回滚镜像。持久化文件卷不随容器删除。

当前不估算确定工期：阶段 2 的公式、渲染和授权结论会显著影响工作量。可先交付经过验证的格式与引用检测，再交付经过渲染验证的页面级检查，但每次发布必须公开真实能力边界。

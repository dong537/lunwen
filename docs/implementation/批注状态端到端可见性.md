# 批注状态端到端可见性

## 目标与范围

论文作者查看每条格式问题时，应能分辨该意见是否已写入可下载的 Word 批注，以及未写入的原因。本次只补齐批注状态从写入器到检测结果列表的传递，不改变检测判定、批注锚点能力或问题分组策略。

成功标准：每条待处理结果都能按规则 ID、OOXML 部件名和结构路径找到唯一批注状态；正文批注显示已写入，页眉页脚等不支持锚点显示未写入及原因；无批注请求时不伪造状态。

## 数据所有权与边界

- `CheckResult` 持有检测结论及原文 `SourceAddress`。
- `CommentWriter` 是批注状态的唯一事实源，负责返回 `WRITTEN`、`UNSUPPORTED_ANCHOR` 或 `REJECTED` 及原因。
- `InspectionService` 将检测结果与批注状态组合进 API 响应，不自行推断写入成功。
- React 只按 `ruleId + source.partName + source.elementPath` 关联结果和批注状态，不将临时 UI 状态作为事实源。

## API 契约与数据流

DOCX → `InspectionKernel` 生成 `CheckResult` → `CommentWriter` 按原始部件路径写入并返回状态 → `InspectionService` 将状态加入 `annotation.items` → 前端问题详情显示状态和原因。

`annotation.items` 每项包含 `ruleId`、`status`、`reason`、`source`。`source` 保留部件名和结构路径；批注状态必须与该地址对应。`annotate=false` 时 `items` 为空，下载地址为空。检测失败仍走现有 API 错误契约。

## 风险与验证

- 同一段落多条规则结果仍共用一个 Word 批注范围，但每条结果保留各自状态。
- 非 `word/document.xml` 锚点继续拒绝写入，必须在前端明确显示，不扩大到未经 Word/WPS 验证的页眉页脚批注。
- 后端 `mvn -B -ntp verify -f backend/pom.xml`：57 项测试通过；前端 `npm run build` 通过。
- 真实论文 `paper1.docx` 的浏览器流程：API 返回 200，3276 条检测结果中有 939 条待处理结果、884 个唯一批注状态；逐项按规则 ID 和原文结构地址核对，缺失状态为 0。880 条状态为 `WRITTEN`，4 条为 `UNSUPPORTED_ANCHOR`。
- 下载副本为 13,463,504 字节，DOCX ZIP 完整，含 `word/comments.xml` 和 522 个批注范围。Chromium 页面无运行时异常；390px 视口没有横向溢出，首条问题可展开并显示未写入原因。
- 以上是单篇真实论文的集成证据，不代表对所有 Word/WPS 版本或任意论文格式均已验收；暂不支持的锚点仍需通过人工核对。

## 本轮审计补充

页码字段识别原来要求单个 `w:instrText` 的内容必须恰好为 `PAGE`，会漏掉跨多个指令节点拆分的字段及 `w:fldSimple`。现已按完整指令识别带开关的 PAGE 字段，并增加真实 docx4j 解析测试；测试先确认旧实现漏检，再验证修复通过。页码字体/字号仍按当前 footer XML 的解析逻辑提取，页脚样式继承及 PAGE 字段与同一页脚中多个段落/格式 run 的精确绑定仍需独立审计。

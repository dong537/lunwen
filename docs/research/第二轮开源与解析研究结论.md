# 第二轮开源、XML 准确性与效率研究

日期：2026-10-04。范围：研究与技术取舍，不进行产品/UI 设计、业务编码或最终技术栈冻结。

## 1. 结论与证据等级

优先组合成熟解析组件与本校独立规则，不直接 fork 一个演示型论文检查网站。Java/docx4j 是值得优先实测的候选，C#/Open XML SDK 保留为比较路线；不再仅凭语言偏好选型。

本次完成 GitHub 项目元数据、核心源码、相关测试源文件、许可证与上游变更记录的静态核查。来源正文保存在 `2026-10-04/`，多数 contents API 响应同时记录 blob SHA。测试源码已阅读，不代表本机运行通过；上游性能数字和案例自述不等于本项目测量。

未运行 Java/C# 检测器，未开展 Word 渲染对照或吞吐基准。当前证据足够筛选候选与识别风险，不足以宣称百分之百准确或性能最优。

fast-context 已安装但上次实测缺少登录凭据，当前会话未暴露搜索工具；本轮直接使用 GitHub API、精确文本查阅和已保存的学校 XML 证据。没有反复重试失效认证。

## 2. 最有价值的项目

### docx4j：主解析候选

仓库：https://github.com/plutext/docx4j

- 核查时默认分支为 VERSION_17_2_1，POM revision 为 17.2.1；不等于已核实 Maven 发布制品。已读 legals/LICENSE，Apache 2.0。
- 上一轮 master 上的旧源码不能代表当前实现。本次保存当前 PropertyResolver、样式顺序测试、表格条件样式测试及 CR-015 变更记录。
- 当前解析器处理默认段落样式、字符样式叠加、段落标记与文字区别、缓存与样式循环等；上游有针对这些行为的断言。
- 关键边界：PropertyResolver 类注释明确表示，表格样式不在这里应用到段落，导出路径由 ParagraphStylesInTableFix 处理。因此只调用 getEffectiveRPr 不足以完成全篇审查。
- 当前解析器返回的部分对象被缓存共享；检测过程不得直接改写返回对象。需要变换时用隔离副本，并保留原始节点到派生节点的映射。

可复用：OPC/JAXB 对象模型、常规有效格式、编号和表格样式处理的现成能力。需要补足的是学校规则、证据链以及经验证的表格上下文集成，不是从零重写整个 Word 标准。

源码：[PropertyResolver](https://github.com/plutext/docx4j/blob/VERSION_17_2_1/docx4j-core/src/main/java/org/docx4j/model/PropertyResolver.java)。本地证据：docx4j-properties.txt、docx4j-order-tests.txt、docx4j-table-tests.txt、docx4j-resolution-design.txt。

### PaperFormatDetect：最贴近学校业务的参考

仓库：https://github.com/siyuanzhou/PaperFormatDetect

- README 自述基于大连理工大学项目，C# + Open XML SDK，检测超过 6000 篇论文；此数字未经本次独立验证。
- 已读 BSD-3-Clause LICENSE。仓库元数据最后推送为 2021 年，业务和依赖需要重新评估。
- 有封面、摘要、正文、图、表、公式、参考文献、页眉页脚等业务模块，可以参考检查项组织。
- Util.cs 存在 static errorLists、paperPath、fs、errorReport、pageDic 等任务状态以及固定 D 盘路径，直接放进多用户并发服务有串数据风险。
- correctRunFonts 的注释按整个 run 是否全为数字/字符选择中西文字体，不足以证明混合 run 中每个字符都检查正确。
- PageLocator.cs 使用 Microsoft.Office.Interop.Word 获取段落末端所在页，再按文本 IndexOf 查找页面；重复段落和跨页段落需要专门验证，不能承诺精确定位。

建议：借鉴规则分类与真实流程，避免继承旧网站和全局状态。当前不推荐直接 fork 作为生产底座。

### transpect/docx2hub：规范化 XML 与旧公式研究参考

仓库：https://github.com/transpect/docx2hub

- README 明确为 DOCX 转 flat hub XML 的库，使用 XProc/XSLT，并非独立格式检查器。仓库元数据标记 BSD-2-Clause，实际引入时仍须逐组件确认许可证。
- 已读 mathtype2mml.xpl：通过 Equation OLE 对象关系、WMF 和自定义字体映射转换为 MathML，并产生校验报告。
- 该流程存在替换对象及清理原始媒体/关系的选项，不能在论文原件上执行；派生表示也不能代替原始格式证据。
- 转换依赖额外 mathtype-extension；本轮按文档路径查找该扩展未找到，尚未完成可运行依赖闭环。

建议：优先研究旧公式处理与来源映射，不把整个 XProc 技术栈直接塞入第一版服务。

## 3. XML 准确性的正确路径

### 校规判定与 Word 显示行为分开

规范明确文字和用户确认的四边 2.6 cm 是判定来源。XML 标准规定的默认行为可按标准解析，并标明来源；这不等于用业务默认值掩盖未知。无法证明的字段保留 unknown。

三个产物分开：原始 XML 属性、有效格式、固定环境下的渲染事实。不要用转换后的 HTML/PDF 反推所有 Word 属性，也不要用标准校验通过代替学校格式合格。

### 解析不是只读 document.xml

1. 校验包与关系，识别命名空间及兼容能力；原件只读。
2. 正确选择 AlternateContent 的有效分支；学校模板中 57 对文本框不能双计。
3. 解析 styles、numbering、theme、settings、fontTable、各节和页眉页脚；脚注、文本框、表格独立归属。
4. 计算属性继承：默认、表格条件、编号、段落样式、字符样式、直接格式；遵循每种属性的特殊合并/toggle 规则。
5. 中西文混合 run 按字符片段分开取字体，处理主题字体、hint、复杂脚本；字体请求与实际替换分别报告。
6. 建立章节/题注/引用索引；样式错误不能导致该标题逃过标题规则检查。
7. 每个结论记录原始部件、节点、文字偏移、继承链、实际值、规则版本和适用范围。

字段例子：小四字号对应 sz=24；2 字符缩进对应常见 firstLineChars=200；1.5 倍行距对应 line=360 且 lineRule=auto。相同数字但不同单位/类型不能视为相等。

四边 2.6 cm 对常见整数 twips 编码量化为 1474；学校模板第 7 节 right=1418 必须报错。严格指语义严格，不是要求 XML 标签、属性顺序或写法逐字相同。

### 公式与版面不能靠 XML 一步完成

- OMML 读取结构；Equation.3 等对象需要进一步读取二进制内容；图片公式没有可直接读取的文字格式。
- 公式编号和引用可先由外围结构确定，但不能将公式预览图片误计为普通插图。
- Word 的最终换行、分页、浮动图片位置、公式和编号的相对位置需要排版环境。
- 渲染器和字体版本固定并记录；LibreOffice 预览与 Word 结果分别标识。
- XML→页面坐标映射必须独立验收；重复文本不能只靠全文查找定位。

不能合理承诺任意文档零误差。可交付的保证是：支持范围内的规则有独立真值样本、结果可重现、不能确定时明确复核，不产生虚假的“全部通过”。

## 4. 哪种处理架构更高效

先比较候选，再做设计。以当前单校、核心检查范围，推荐进入试验的是“模块化单体代码库 + 独立 worker + 按需渲染”，不是已经冻结的部署方案。

| 候选 | 优点 | 主要代价 | 本次判断 |
| --- | --- | --- | --- |
| HTTP 请求中同步完成 | 开发直观 | 长文档占用请求；超时、重启恢复和峰值内存难控 | 不推荐正式服务 |
| 单代码库，持久化任务，解析与渲染分池 | 少量部署组件；资源隔离；可横向增加 worker | 需要幂等、事务与覆盖状态 | 优先验证 |
| 微服务 + 消息总线 + 多级分布式缓存 | 适合多团队和已有大型平台 | 增加运维、网络与一致性复杂度；不改善 XML 语义 | 当前没有采用依据 |

推荐研究流水线：

```text
上传并保存不可变原件
  → 事务创建任务
  → 安全解析包 + 有效格式计算
  → 带来源的规范化文档与索引
  → 按对象类型执行确定性规则
  → 仅为需要的规则运行隔离渲染
  → 合并结果、覆盖状态及证据
```

性能关键点：

- 一份文档只建一次解析模型；规则不重复打开 ZIP，不逐条全量 XPath 扫描。
- 样式链和主题按文档缓存；表格条件、字符范围、编号等上下文进入键。不能把 styleId 相同误当作有效格式相同。
- 已有 docx4j 有效模型时不要再常驻第二份完整 DOM。底层 XML 查询集中在 adapter，仅为未暴露属性按需读取；原始 bytes/节点定位用于证据。
- 小型确定性检查通常顺序执行，文档之间有界并发；渲染分池、限时、限内存，不为每个段落创建线程。
- 同文档改规则可复用解析结果；升级解析器、渲染器、字体或修订视图使相关缓存失效。
- 不缓存丢失授权上下文的共享报告；文件去重不允许跨用户访问。
- PostgreSQL 持久化任务可减少 Redis/Kafka 依赖；业务写入与任务调度必须验证同事务，任务按可能重复执行设计。
- 每任务临时目录独立；报告原子发布。失败重试不复制结果、不覆盖原件。

“最快”的结论只能通过测量获得。对普通、长篇、图像密集、公式密集文档，分别测 1/2/4 并发下的解析、样式计算、规则、渲染耗时，统计 p50/p95、RSS 和失败率；对照同步/后台池两种执行方式，选择满足校方等待时间和硬件成本的配置。

## 5. 进入正式设计前的门槛

1. 将学校规则分为明确硬规则、建议项、歧义项；用户已确认边距无需重复询问。
2. 用 docx4j 与必要的独立标准/Word 对照验证样式继承、中西文、表格条件、编号和兼容分支。
3. 用模板两种旧公式确认支持范围，保留无法判定项；不把数学转换成功当作原始格式保真。
4. 固定 Word/WPS 权威显示环境；渲染器对照结果决定页面级承诺。
5. 取得独立标注真实论文，逐规则报告误报、漏报和未知覆盖率；同时做性能基准。
6. 通过后再冻结技术栈、模块接口、部署拓扑与页面流程。

目前缺少独立标注真实论文和渲染对照证据。研究可以完成，精度/吞吐验收尚未完成；不得据此宣布检测产品可交付。下一步应是隔离的解析能力试验，而不是先生成界面。

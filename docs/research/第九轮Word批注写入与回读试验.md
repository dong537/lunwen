# 第九轮：Word 批注写入与回读

日期：2026-10-07。范围：固定学校规范 DOCX 的批注副本研究，不修改原件，不进入生产接口。

## 结论

在原件副本上写入一条标准 classic comment 的 XML 结构可被 docx4j 重新读取。批注包括 `word/comments.xml`、正文的 `commentRangeStart/End` 与 `commentReference`、正文关系以及 `[Content_Types].xml` 声明。原件其他 DOCX 部件解压后字节保持一致。

批注样本针对第 7 节右边距问题，写入位置为正文第 115 个直接段落（第 7 节标题）。批注正文说明实际 1418 twips（约 2.5 cm）、要求 1474 twips（2.6 cm）以及修改路径；它没有直接修改论文页边距。

## 验证结果

- Python 批注测试 5 项通过：结构范围与 ID 一致、原件内容保护、已有批注保留并分配新 ID、错误哈希拒绝、空文字段落拒绝。
- 重复文字测试通过：向其他段落加入与目标相同的文本后，批注仍只落在第 115 个结构段落，没有使用全文文本首次匹配。
- Java/docx4j 独立回读测试 1 项通过：能取得 CommentsPart、批注作者、数量及主文档关系。
- 原件 SHA-256 仍为 `3c9c3dc012b779b4ebd20ea35cb86142d73fb911c7733e3b0d1789ce2d6ac2b2`；原件文件没有写入。

证据位于 `research-spikes/comments/evidence/`，样本输出位于 `artifacts/论文规范-格式筛查批注试验.docx`。输出 ZIP 的压缩字节会变化，这是重新打包的结果；比较的是解压后的部件内容。

## 重要限制

本轮验证了固定正文直接段落的整段锚点。还没有验证：字符范围跨多个复杂对象、文本框、超链接、域、修订、页眉页脚、表格单元格、已有交叠批注、现代 threaded comments、数字签名、Word/WPS 实际显示及打开时的修复提示。遇到签名、现代批注元数据或已有交叠锚点，研究写入器会拒绝而不是覆盖。

本机没有检测到 Word、WPS 或 LibreOffice 可执行文件，所以无法作编辑器级结论。docx4j 能打开只证明当前 OPC/XML 关系可读，不证明 Word/WPS 视觉和交互兼容。

批注 API 必须接收检查结果中的稳定原始证据地址，不能重新按文本查找；来源哈希变化时拒绝写入。无法可靠锚定的结果保留在 HTML 报告，并注明“未写入 Word 批注”的原因。

## 对正式系统的建议

批注写入应作为 reporting 的独立 adapter：

```text
已发布 CheckResult（原始部件/元素地址）
  → AnchorResolver（确认地址仍属于同一原件）
  → CommentWriter（只修改副本及必要 OPC 部件）
  → StructuralVerifier + docx4j 回读
  → 带批注 DOCX 下载
```

它不能接收经过表格样式预处理后重新序列化的工作模型作为唯一输入。每次批注输出记录源文件哈希、结果版本、写入器版本、写入/拒绝数量和拒绝原因。完成 Word/WPS 实机验收前，产品界面应把输出标记为“结构验证通过，编辑器兼容性待复核”。

后续优先级：在安装 Word 或 WPS 的受控环境中打开样本并保存回读；增加表格、页眉页脚和文本框的锚点测试；再决定是否扩大到字符级批注。当前样本不代表全部 DOCX 批注能力已完成。
